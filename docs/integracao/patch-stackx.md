# Patch de integração — stackx × mergex

Prompt pronto para colar no repositório da skill `stackx`. Ele altera a `stackx` para descobrir e registrar o **dialeto de versionamento** do repositório, que é o que a `mergex` consome.

Trabalhe de forma autônoma até o fim: não faça perguntas, não peça autorização para editar arquivos, não pare no meio.

---

## PARTE 1 — O CONTRATO

A `stackx` descobre o dialeto técnico do repositório e grava em `docs/stack/CONVENCOES.md`.

A `mergex` cuida do versionamento e da entrega. Ela é a skill que mais depende desse dialeto, porque é a única que escreve **no repositório** — branch e commit — em vez de escrever só em `docs/`. Uma branch com o prefixo errado ou um commit fora do padrão do time é ruído que a `mergex` produz sozinha.

**Convenção do repositório vence a convenção padrão da `mergex`.** A `mergex` tem padrões próprios para funcionar em repositório sem `CONVENCOES.md`; ela não os impõe onde já existe um jeito de fazer.

### A regra do PROPOSTA

O `CONVENCOES.md` distingue o que foi **observado** no repositório do que foi **proposto** pela `stackx`.

**Ponto marcado como `PROPOSTA` não governa a `mergex`: vira aviso, não bloqueio.** Uma proposta é uma sugestão de padronização que o time ainda não adotou; se ela governasse, a `mergex` estaria impondo uma decisão que ninguém tomou.

Essa distinção precisa estar **explícita e legível** no `CONVENCOES.md`, ponto a ponto — é o que este patch garante.

### As duas regras deste contrato

**1. Ausência da `mergex` nunca muda a `stackx`.** O que este patch acrescenta é descoberta de convenções que valem por si: qualquer pessoa ou skill que vá criar branch ou escrever commit se beneficia delas.

**2. O comando de revisão NUNCA é encadeado.** A `stackx` não menciona, não sugere e não aciona `/mergex-revisar` em lugar nenhum.

## PARTE 2 — O QUE ALTERAR

### 2.1 Descobrir o dialeto de versionamento

Acrescente ao roteiro de descoberta da `stackx` um eixo novo: **versionamento**. Ele responde a seis perguntas, cada uma com um comando concreto.

> ### Eixo: versionamento
>
> **1. Como este repositório nomeia branch?**
>
> ```
> git branch -a --format='%(refname:short)'
> ```
>
> Observe prefixo (`feature/`, `feat/`, `bugfix/`, `hotfix/`, `chore/`), separador (`/`, `-`, `_`), e se há identificador de ticket no nome. Registre o padrão predominante, com a contagem que o sustenta.
>
> **2. Qual é a branch base?**
>
> ```
> git symbolic-ref refs/remotes/origin/HEAD
> ```
>
> Registre o nome. Observe também se o repositório usa uma branch de integração distinta da principal (`develop`, `staging`).
>
> **3. Como este repositório escreve mensagem de commit?**
>
> ```
> git log --format=%s -50
> ```
>
> Observe: usa Conventional Commits (`tipo(escopo): titulo`)? Prefixo de ticket (`[OC-2026-0184] ...`)? Qual idioma? Há corpo além do título? Registre o padrão predominante e o vocabulário de tipos efetivamente usado — não o vocabulário canônico, o que este repositório usa.
>
> **4. Qual é o comando da suíte de testes?**
>
> Do manifesto do projeto (scripts de `package.json`, `Makefile`, `pyproject.toml`, configuração de CI). Registre o comando que roda a **suíte inteira**, não o que roda um arquivo.
>
> **5. Que arquivos este repositório gera automaticamente?**
>
> Lockfiles, snapshots, clientes de API gerados, código de ORM, arquivos com cabeçalho "generated by", entradas marcadas `linguist-generated` em `.gitattributes`.
>
> **Este ponto exige rigor**: um arquivo declarado como gerado é dispensado da revisão humana por outras skills. Na dúvida, **não** o declare gerado. E atenção ao caso que mais engana: **migração de banco gerada por ORM continua sendo migração** — ela tem efeito próprio no banco e nunca é dispensável.
>
> **6. Qual é a estratégia de merge?**
>
> ```
> git log --merges --format=%s -20
> ```
>
> Observe se o repositório usa merge commit, squash ou rebase. Registre o que o histórico mostra.

### 2.2 Registrar cada ponto com o estado explícito

No `CONVENCOES.md`, cada ponto do eixo de versionamento leva um **estado explícito**:

> | Estado | Significado | Efeito em outras skills |
> |---|---|---|
> | `OBSERVADO` | O repositório faz assim, e há evidência no histórico | **Governa.** Outras skills seguem |
> | `PROPOSTA` | A `stackx` sugere padronizar assim; o repositório ainda não faz | **Não governa.** Vira aviso |
> | `NAO DETERMINADO` | Não foi possível descobrir | Outras skills usam seus próprios padrões |

Forma sugerida para a seção:

> ## Versionamento
>
> | Ponto | Convenção | Estado | Evidência |
> |---|---|---|---|
> | Nome de branch | `feature/<slug>`, `fix/<ticket>-<slug>` | OBSERVADO | 23 de 27 branches |
> | Branch base | `main` | OBSERVADO | `origin/HEAD` |
> | Mensagem de commit | Conventional Commits, em português | OBSERVADO | 44 dos últimos 50 |
> | Tipos usados | `feat`, `fix`, `chore`, `refactor` | OBSERVADO | histórico |
> | Comando da suíte | `npm test` | OBSERVADO | `package.json` |
> | Arquivos gerados | `package-lock.json`, `src/api/gerado/` | OBSERVADO | `.gitattributes` |
> | Estratégia de merge | squash | PROPOSTA | histórico misto; sugestão de padronizar |
>
> A coluna **Estado** é lida por outras skills. `PROPOSTA` não governa: vira aviso.

A coluna **Evidência** existe para o mesmo fim que em toda a `stackx`: uma convenção sem evidência é opinião.

### 2.3 `SKILL.md` — uma seção nova ao fim

> ## Versionamento e entrega
>
> O eixo de versionamento do `CONVENCOES.md` — nome de branch, branch base, formato de commit, comando da suíte, arquivos gerados e estratégia de merge — é consumido pela [`mergex`](https://github.com/AxisGov/mergex), a skill que cria a branch, commita cada task e abre o pull request.
>
> **Convenção `OBSERVADO` governa** a `mergex`: ela segue o repositório em vez do próprio padrão. Ponto marcado como `PROPOSTA` **não governa** — vira aviso, não regra —, porque uma proposta é uma padronização que o time ainda não adotou.
>
> A `stackx` não chama a `mergex` e a `mergex` não chama a `stackx`: o que existe é leitura de artefato. Sem a `mergex` instalada, nada muda aqui.

### 2.4 O que NÃO alterar

- **Nenhuma regra da `stackx`.** Nenhum critério de descoberta, nenhuma exigência de evidência.
- **Os eixos existentes.** O de versionamento é acrescentado, não substitui nenhum.
- **A distinção observado × proposta.** Este patch a torna explícita por ponto; não a inventa.
- **Nada sobre executar versionamento.** A `stackx` **descobre e registra** convenções; ela não cria branch, não commita e não abre PR.

8. Simule a `stackx` **sem** a `mergex` instalada: o `CONVENCOES.md` é produzido normalmente e nenhum passo falha.
9. Confirme que nenhum eixo ou critério existente da `stackx` foi alterado.
